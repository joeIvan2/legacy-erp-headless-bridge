# Milestones

這份紀錄說明專案如何從「看得到的桌面操作」演進成「可組合的 Headless 能力」。細節刻意停留在工程決策層級，避免揭露原廠程式或企業資料。

## 1. 從 Read-only SQL 理解最原始資料

第一步不是模仿畫面，而是確認資料真正落在哪裡，以及一張銷貨單由哪些持久化資訊共同構成。

- 以唯讀帳號探索 schema 與關聯。
- 從單號反查客戶、品項、數量、價格與合計。
- 建立可重複的核對方式，區分「畫面顯示值」與「持久化資料」。
- 明確規定 SQL 不負責建立正式單據。

這一階段提供後續每次自動化結果的獨立證據。

## 2. 反編譯與互通性分析

接著針對合法持有、合法部署的 Delphi 32-bit ERP 安裝進行靜態分析，理解 EXE、DFM 表單資源、資料集、型別與商業元件之間的邊界。

- 反編譯只用來定位責任與呼叫關係。
- 尋找可沿用的既有商業規則，而不是重新仿製原廠程式。
- 把 UI 顯示、資料讀取與單據 mutation 分成不同層次。
- 所有分析產物、原廠 Binary 與內部位址都留在受控環境，不進 Showcase。

## 3. 以 GUI Automation 完成概念驗證

早期版本先用滑鼠、點擊、鍵盤與畫面焦點串起完整流程，快速證明「輸入一份結構化訂單後，可以得到正確銷貨單」。

這個階段也暴露桌面自動化的限制：解析度、彈窗、焦點、遠端桌面狀態與使用者同時操作，都可能改變結果。

## 4. 移除座標、滑鼠與鍵盤依賴

確認流程後，逐步將每個 UI event 換成穩定的程式邊界。最終正式 CLI 路徑不再發送滑鼠或鍵盤事件，也不靠畫面座標找欄位。

重要成果不是「讓畫面點得更快」，而是讓業務動作不再依賴畫面是否位於前景。

## 5. 建立 Headless CLI

登入狀態、銷貨單查詢、建立與驗證被整理成固定 JSON contract。

- 輸入先通過 schema 與業務前置檢查。
- 帳密只由 Windows 主機本機工作階段讀取。
- 查詢每次重新讀取，不預抓正式單據。
- mutation 使用唯一請求識別與確認資訊。
- 逾時或結果不明時只允許核對，不允許盲目重送。

CLI 成為後續所有介面的穩定接點。

## 6. 接上 Discord 與遠端裝置

Discord Bot 不直接理解 ERP 內部結構，只負責把文字、圖片或結構化訂單轉成經過驗證的命令，再交給同一個 CLI 核心。

macOS 端採用薄客戶端：原廠 Windows Library 留在 ERP 主機，Mac 透過受控 SSH／JSON 邊界操作，因此不需要也不會取得 ERP 密碼。

## 7. 建立 Flask Web 版本

Web 版先完成唯讀銷貨單，沿用既有查詢核心，不重寫 ERP 資料規則。它是由 Flask API 與瀏覽器 HTML／CSS／JavaScript 實際組成的網頁，不是 RDP、VNC、截圖串流或包裝原版 EXE。

- 依桌面版表單資訊層次重建版面。
- 依反編譯取得的 DFM 位置、尺寸與父子層級重建可比對框架。
- 前端框架固定，只替換目前單據資料。
- 客戶名稱可模糊搜尋，但使用者必須確認正確 ID。
- `Ctrl + ↑ / ↓` 在已選客戶的即時結果內切換。
- 不預抓下一張單，避免資料已變更卻仍顯示舊內容。

## 下一步

- 補上手機尺寸的實際操作與響應式版面展示。
- 將 Web 的建立流程放在同一套確認與 reconciliation 規則後方。
- 視部署需求提供 Rust 薄客戶端；Windows ERP 執行節點保持不變。
- 持續把實際部署資料與 Showcase 文件完全分離。
